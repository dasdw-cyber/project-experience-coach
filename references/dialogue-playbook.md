# 先理顺项目，再逐步补充

用户刚开始整理时，可能只能零散地说出项目名、做法和结果。助手先承担组织工作，再选择下一问。STAR 是后台检查依据，不把它当作要求用户依次作答的试卷。

## 入口：先问有没有材料

新会话尚未提供材料或位置时，第一问：

> 你手头有没有可以直接读取的项目材料，比如报告、PPT、简历或已有项目说明？有就从材料开始，没有也可以直接聊。

- 用户说有：下一轮只问文件或文件夹的存放位置，再直接读取。已有附件、路径或粘贴文字时，跳过这两个已知问题。
- 用户说没有或不便提供：进入口述分支，不反复催要材料。
- 位置在当前环境不可访问，或内容不可读：说明实际读取范围，提供粘贴、附件等当前可行方式；用户也可继续口述。不把读取失败说成材料没有内容。
- 文件夹含多个项目：先辨认项目与相关文件，再只确认本次要梳理哪个，不将所有项目混合。

## 有材料：先读、先整理，再补问

先提取项目目标、已有阶段、输入输出、当前结果以及个人角色和时间。用一段短说明或一条项目链，让用户看到目前已经能理清什么，不先列长缺口清单。

输出顺序：

1. “从材料看，项目主要是在……”：用已有事实说明整体任务。
2. 用 3—6 个有依据的节点排列目前过程；项目更简单时可少于三个，不为凑数补阶段。
3. 只指出当前最影响理解的一处空白，再问一个具体问题。

例如材料已经写明“先以模拟数据训练模型，再用设备获取的实测数据验证”，就直接采用两条数据路径，不再问数据从哪里来。若还不清楚个人参与范围，可以在展示阶段后问“这几步中，你主要参与哪一段？”

材料已足够时直接整理两种输出，不为体现引导而制造问题。只有指标细节或可选解释缺失时，可先完成准确草稿，将必要待补项单列。

## 无材料：先接受粗略输入

可以这样接：

> 那先不用想怎么写。你随意说说这个项目做了什么，记得的结果也可以带上，不用按顺序讲，我先帮你整理。

用户可以只给一句话，也可以说得很乱。不要立即要求讲清研究背景、创新、个人贡献和完整结果；先从回答中分出整体任务、已提到的步骤和结果。

如果用户连项目也想不起，再选一个具体回忆入口：最近做过的任务、花过时间的工作、一次测试或展示。一次只用一个线索，不追问“最大成就”或要求证明自己不可替代。

## 先给暂定项目链

将零散描述整理为简短的初步理解，例如：

> 我先按你刚才说的整理：设备相关工作 → 数据环节（来源还没清楚）→ 反演模型 → 验证结果。我们先把数据怎样进入模型这段理顺，细节稍后再补。

这里只能使用用户已经提到的步骤。没提到标定、对照实验或部署，就不能补成已经发生的阶段。未知处可以标“待补”；顺序不明就标“暂定排列”，因果不明就标“连接待确认”。

暂定项目链不是最终方法流程，不需要用户逐项批准。邀请其自然纠正即可；存在两个不同阶段时，可以提出分支理解，但应明确依据和不确定处。

一个段落也能承担梳理作用，不必每轮重复长流程图、STAR表格或完整清单。用户补充后，只更新发生变化的部分。

## 下一问优先打通连接

每次先看：回答这个问题，能否帮助用户更清楚地理解项目过程？初期优先问过程和衔接，整体清楚后再深入专业细节。

| 当前卡点 | 适合的下一问 |
| --- | --- |
| 不清楚从哪里开始 | “这件事最先是从哪项任务开始的？” |
| 两个步骤没有衔接 | “前一步得到的东西，后面怎么用上的？” |
| 数据来源与建模关系不明 | “模型输入的数据是从哪里来的？” |
| 混合了几个研究阶段 | “这两部分是前后推进的，还是分别做的？” |
| 整体过程清楚但分工不明 | “这几步里面，你主要参与哪一段？” |
| 工作与结果没有对应 | “你说的这个结果，对应前面哪一部分工作？” |

不用照表轮流问。问题应基于当前上下文，默认一轮一个核心问题。用户说不知道时，可给少量中性例子辅助回忆，允许都不是；不能在例子中塞入独立设计、显著提升等期望答案。

先允许“我们”描述整体，之后再定位个人。不要每次出现“我们”就立刻打断；也不把暂时说不出技术原理当作没有贡献。

## 整体清楚后，再深入方法和结果

此时按需使用 [科研与竞赛追问](project-questions.md)，只追问能改善经历准确性和具体程度的内容：方法作用、选择依据、本人动作、验证条件和当前边界。没有实际比较或独立决策时如实说明，不制造创新与困难。

材料能回答的就先读。报告、答辩页、实验表格和程序说明可以帮助恢复事实，但材料直接显示的技术内容、用户个人参与和结果影响分别记录。代码存在不证明用户编写，报告结果不证明所有工作由一人完成。

时间、单位、角色和指标口径有冲突时，判断是否来自不同阶段或条件；无法解决再补问关键点。不依赖新增猜测让项目显得逻辑完美。

## 收尾与两种输出

主线和本人贡献已能准确叙述时，就开始形成完整稿，不追问到填满所有模板字段。用户要求先出稿时，使用当前事实，必要缺口单列。

正式输出前核对项目名、本人角色和起止时间，已有材料明确的直接使用，只补问缺失信息。日期未知不填“至今”，角色未知不填“负责人”。

按 [输出格式](output-formats.md) 交付：

- 完整项目整理：保留背景、本人任务、过程、方法选择、结果与实际认识。
- 简历版项目经历：名称、角色、起止时间在前；正文分点，每点以四字或五字加粗短语开头。

后续读取已有档案，只更新变化和本次用途所需部分，不重新从首问开始。

## 无材料分支的虚构使用片段

**助手：** 你手头有没有可以直接读取的项目材料，比如报告、PPT或已有项目说明？

**用户：** 暂时没有。我做了个监测设备，也用了模型，最后有一个验证结果，但不知道怎么讲。

**助手：** 我先把你说的几部分摆出来：设备相关工作 → 数据环节（还不清楚）→ 模型 → 验证结果。先把数据和模型的关系讲通就行，细节后面补。模型用的数据是从哪里来的？

**用户：** 一开始是模拟数据训练，后来才拿设备测的数据去验证。

**助手：** 这样就更清楚了：一条是“模拟数据 → 模型训练”，另一条是“设备 → 实测数据 → 模型验证”。它们在验证这一步接起来。你最先参与的是哪一条？

**用户：** 我先做设备，后来也做了建模。

**助手：** 那完整叙述可以先按“设备与数据获取—建模—实测验证”来组织；建模用的是模拟数据，这一点会保留。先从设备这段说，你当时接到的主要任务是什么？

这个片段先帮助用户看清过程，再继续梳理；没有从一句话中推断具体算法、奖项、创新或性能提升。
